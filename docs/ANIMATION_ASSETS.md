# アニメーションの事前生成画像

## 通常の起動

従来どおり `launch.bat` または `npm start`。生成済みの `assets/characters/` を同梱しているため、プレイにPythonや追加パッケージは不要。8種類・4方向・待機/歩行/攻撃の1,648コマを1種類1画像のアトラスに収める。コマ数・周期・攻撃のキー・足元原点はStudioの実装を維持する。

描画DPRは1または1.5。実DPRが1を超える端末は1.5の画像を使い、CSS上のマス75×42px・駒倍率1.25は変えない。従来の上限1.5を維持し、1.25などの中間値だけは1.5へ切り上げる。両組の画像を同時に読むことはない。

## 再生成（開発時だけ）

1. Node.js 18以上、WebP対応のPython/Pillowを用意する。今回の生成環境はPython 3.12.1・Pillow 12.0.0。未導入の場合は `python -m pip install Pillow`。
2. `npm run assets:build` で127.0.0.1:8160専用の生成サーバーを起動する。
3. 開いたブラウザで「16枚のアトラスを生成」を押す。`complete: true` の表示後、サーバーをCtrl+Cで終了する。
4. `npm test` と `/tests/atlas-qa.html` の照合を行う。生成済み画像・manifestと描画コードを一緒に管理する。

Pythonなしでは `npm run assets:build -- --png` でPNGを生成できる（通信量は増える）。`--no-open` はブラウザ自動起動を省略する。通常のゲームサーバーには書き込みAPIを追加していない。

`tools/export-atlases.js` が実際のStudio定義と既存キャッシュ生成処理をブラウザCanvasで実行する。元フレームの画素をgetImageData/putImageDataで直接転記し、別の画風や左右反転を使わない。`tools/encode-atlas.py` はPNGを可逆WebPへ変換し、変換前後のRGBA全画素一致を確認してから保存する。ゲームの乱数処理には触れない。

`manifest.json` には入力描画コードのSHA-256、画像のSHA-256、解像度、方向、コマの位相、足元原点、描画設定を記録する。`tools/atlas-source.mjs` は現在の入力コードを列挙し、`npm test` で生成忘れを検出する。画像ファイル名にも内容ハッシュを含める。

新しい生成は新しいハッシュのファイルを書き、manifestを最後に更新する。既存ファイルを自動削除しない。過去の生成物を整理する場合は、manifestにないことを確認する。

## ゲーム側の接続

- `src/ui/kingdom-atlas.js`: 選択解像度の8画像を取得・デコードして登録。画像またはメタデータが壊れている場合は、その種類だけ従来の生成へ戻る。取得/デコードに15秒の上限を設ける。診断は `Board.diagnostics.atlas`。
- `vendor/inkstone/src/rendering/cache.js`: アトラスを受け入れる入口と矩形によるフレーム参照を追加。定義・方向・周期・倍率・原点の不一致は拒否。元のコマ選択処理はそのまま利用する。
- `renderer.js` / `character-view.js`: Canvasまたはアトラスの矩形を同じ実画素位置へ貼る共通関数を利用。影・透視・半透明プレビュー・矢・魔法の演出も維持する。
- `serve.mjs`: ハッシュ付きの画像だけ1年間のimmutableキャッシュ。manifest・コードはno-storeのままなので更新を確認できる。別のホスティングでは同等のヘッダー設定が必要。

## 検証と制限

`npm test` は生成元/画像ハッシュ、全1,648コマ、周期・足元・方向、不正なメタデータの拒否、同期生成なしのフレーム選択を検査する。`/tests/atlas-qa.html` は2解像度全3,296コマを元の描画と照合し、本番ローダーと不正な画像情報からの復帰も検査する。半透明色のpremultiplied RGBAと通常RGBAの往復に伴う8bitの丸め差は2階調以内とし、それを超える画素は不合格。WebP圧縮自体はPNGとの画素一致を別途確認する。

画像化は主に端末の生成負荷を減らすもので、展開後のRGBAメモリを減らすものではない。アトラス末尾の空白分だけ従来より増える。通信の遅い環境では初回の画像取得が支配的になる可能性があり、実機・遅い回線の検証は別途必要。

測定値・実操作の確認結果は [検証記録](TEST_REPORT.md) に記載する。旧方式の調査は [起動性能調査](STARTUP_PERFORMANCE.md)。
