# 初回キャラクター準備の調査

この文書は2026-10-24の旧方式の調査記録。2026-10-25に事前画像化を実装した。現在の生成方法は [アニメーション画像](ANIMATION_ASSETS.md)、改善後の測定は [検証記録](TEST_REPORT.md) を参照。

2026-10-24、基準コミット `4965d576c039dd02174b203bf98dfa9f2746902d`。今回の作業は原因の調査と改善案の比較。本番コード・ルール・キャラクターの描画定義は変更していない。

## 結論

タイトル表示前に、8種類×4方向×待機/歩行/攻撃の全1,648コマをCanvasへ生成する処理がある。キャラクター画像のダウンロード待ちではなく、端末内での描画準備が起動の主要な待ち区間になっている。キャッシュはページ内だけなので再読み込みでも作り直す。

`src/ui/kingdom-board.js:32` の `init()` は背景、肖像、タイトル画を用意した後、8種類それぞれの `prepareCaches()` を待ってからreadyにする。`src/ui/app.js:951` はこの完了後にボタンのイベントを登録し、タイトルを表示する。`vendor/inkstone/src/rendering/cache.js:28` は1種類分の全コマを同期生成する。種類の間にある12msのsleepは、種類内の長い処理を分割しない。

- 59リソース、本文合計623,407バイト。キャラを準備している区間には通信は完了している。
- 1回目の1種類分の同期生成は102〜349ms。Long Tasksでも停止区間を確認した。剣士は240コマで最も長い。DPR1.5の実験では、起動中の最長Long Taskは544ms。
- 再読み込み時の背景生成は24ms。DPR1.5で38ms。主因ではない。肖像8体・タイトル6体はliveで1回ずつ描くため、全コマを重複生成しているわけではない。
- JS生成時間の合計と約5.9秒の経過時間には差がある。種類間でタイマーが再開するまでの遅延が観測されるが、GPU処理・Canvasの内部処理・ブラウザのスケジューリングの内訳は今回分離できていない。**約5.9秒すべてをJS描画時間とは扱わない。**
- 実DPR 1のPCで `devicePixelRatio` を診断ページ内だけ1.5に上書きした比較。スマートフォンのCPUやGPU、通信、OSを再現していない。この比較ではDPRを下げるだけの時間短縮は確認できなかった。
- キャッシュ容量は幅×高さ×4の理論値。GPU複製・背景等を含む実プロセスメモリではない。描画DPR 1.5で画素量は約2.24倍になる。
- コンソールの警告・エラーなし。2、3回目は計測中 `document.hidden=false`。1回目はこの状態を記録していない。

## 改善案と順序

1. **最初に必要な絵だけ用意し、残りを小さく分割して生成する。** タイトルは待たずに表示し、盤面の初期方向・待機1コマから準備する。残りは1〜数コマ単位で時間予算を設けて処理する。歩行/攻撃が必要になった際はその動作を優先して用意し、準備中の見た目と入力待ちも設計する。初期応答の改善が狙いであり、全コマを作る総作業量は減らない。既存公開APIは種類単位の全生成なので、取り込み済みcache/rendererへの限定的な変更が必要。
2. **同じStudio描画から、配布前にアニメーション画像を生成する。** 4方向・全コマ・周期/キー・足元原点を保ったPNG/WebP等のスプライトアトラスとメタデータを作り、ゲームでは必要な画像を読み込む。初回にも端末側の大量ベクター描画を省けるため、本格的な待ち時間短縮の有力案。画像の通信量・デコード時間、更新時の生成工程とハッシュ管理は増える。画像化だけで展開後のRGBA容量は減らないので、透明余白の切り詰め、待機/歩行/攻撃ごとの分割、必要時デコードも比較する。画風やコマ数を減らす必要はない。
3. **2回目以降の再利用を追加する。** 事前生成画像なら版付きURLとHTTPキャッシュを使う。実行時生成を維持する場合はIndexedDBへのBlob保存も候補だが、保存/復元コスト、容量制限、定義・解像度・描画設定による失効管理が必要。初訪問には効かない。現行 `serve.mjs:32` は全資産が `no-store` なので再取得も起きるが、ヘッダーだけ直してもCanvasの再生成は残る。

推奨は、まず1でタイトル表示と操作応答を早め、その後2で初回の生成処理自体をなくし、3を組み合わせる進め方。実装量を増やせるなら、2を中心に「待機画像を優先読込・動作別に分割」を行うと二重の仕組みを作らずに済む。短縮幅は実装後の同条件比較と実機で確認する。

避ける対処:

- `prepareCaches()`を外すだけ: `renderer.js:72` の `caches.get()` が初回描画で全コマ生成し、待ち場所が対局開始後へ移るだけ。
- `Promise.all()`だけ: 同期Canvas描画は並列化されない。
- DPR固定・コマ数削減を先に行う: メモリには効きうるが画質や動きに影響する。今回のDPR比較では待ち時間の改善を確認していない。
- Worker化だけ: メインスレッドの停止は緩和しうるが、総描画量は減らない。現行の `document.createElement('canvas')` 等の変更が必要で、互換性と受け渡しを検証する追加コストもある。

## 再計測

`node tests/build-startup-profile.mjs` で現在のindex.htmlから診断HTMLを再生成し、通常のローカルサーバーで `/tests/startup-profile.html` を開く。起動後、右下の診断表示と `#startup-report` にJSONが出る。`?dpr=1.5` は描画解像度の比較用。診断コードは通常URLから読み込まない。

実装後は、タイトル操作可能まで・対局表示まで・最初の移動/攻撃までを別々に測る。画風・全方向・武器の持ち手・足元・移動プレビューの一致、未準備時の連打、背景復帰、実機のメモリも確認する。
